# trainer-feedback-record

トレーナーからのフィードバックを `resource/trainer/feedback/YYYYMMDD.md` に蓄積するためのスキル。

このリポジトリは `CLAUDE.md` に記載のとおり、**トレーナーフィードバックは原文のまま残す**運用になっている。`docs/content/` 配下のメニューやガイドへの反映は別作業。このスキルは**原文の保管**と、**次のトレーニングで何をするかに絞った短いアクション・サマリ**だけを担う。

## 発火する状況

ユーザーが以下のような入力をしたら、このスキルを使ってファイルへ保存する：

- トレーナーからの Slack / メール返信本文を貼り付けてきた
- ジムでのセッション中・直後に言われた内容をテキストでまとめてきた
- 「今日のフィードバックを記録しておいて」「これ feedback に入れて」のように明示された
- 入力に `:white_check_mark:` `:black_medium_square:` のような Slack 絵文字コード、❶❷❸ のような番号付き、トレーナー名の署名が含まれる（トレーナー本文の典型的特徴）

ユーザーがフィードバック以外の話（メニュー相談・体調メモ単体）をしているだけのときは、このスキルは使わない。**ゴルフレッスンのフィードバック**は `golf-feedback-record` スキルの担当なので、このスキルでは扱わない。

## 手順

### 1. 当日の日付・時刻を確認する

`date +%Y%m%d` をシェルで実行して当日の日付（例：`20260426`）を取得する。システムプロンプトの `currentDate` を流用しない（時差や日跨ぎでズレるため）。ファイル名はこの日付＋`.md`。

ユーザーが「昨日のセッションのフィードバック」のように**過去日**を明示してきた場合のみ、その日付を使う。曖昧なら確認する。

同日追記用の時刻は `date +%H:%M` で取得。

### 2. 保存先パスを決める

```
resource/trainer/feedback/YYYYMMDD.md
```

### 3. 既存ファイルの有無で処理を分ける

- **存在しない場合** → 新規作成
- **存在する場合** → 末尾に区切り線を入れて追記する（同日複数回のフィードバックは順序情報も価値があるため上書きしない）

```markdown
---

## 追記（HH:MM 頃）

（以下、新しい原文＋サマリ）
```

### 4. 書き込む内容

ひとつのフィードバックブロックは次の構造で書く。**サマリは短く、行動に絞る**ことを最優先にする：

```markdown
# YYYY-MM-DD トレーナーフィードバック

## 原文

（ユーザーが貼り付けたテキストをそのまま貼る。整形・誤字修正・絵文字コードの置き換えは一切しない）

## 次のトレーニングへの反映

### ストレッチ・ウォームアップで取り入れること
- 種目名 — どこを狙うか（**原文に出ている部位名のみ**）

### ジムメニューで意識すること
- 種目名 — 意識する筋／避けるフォーム（**原文に出ているキューのみ**）

### docs/content/ 反映候補
- どのファイル（`docs/content/menu/gym.md` など）に何を追記すべきかを 1〜3 件
```

各セクションは原文に該当する記述がなければ**省略**してよい（無理に埋めない）。

### 5. サマリ作成時の鉄則

このスキルでは「短く、書いてあることだけを書く」が最優先。以下を厳守：

- **原文に書かれていることだけ**を要約する。推測・補足・一般論・「裏で要請されている筋」のような**読み解き**は一切足さない。書かれていないなら書かない。後から「これは AI の解釈」と分からなくなるのを防ぐため。
- **解剖学用語が原文で略されているとき**は、原文の表記をそのまま使う（例：原文が「内転筋」なら「内転筋」のまま。「長内転筋・大内転筋・薄筋」のように勝手に展開しない）。**ただし**原文に出てこない筋は新たに足さない。
- **キューを言い換えない**（例：原文「肘は多少曲げるだけでよい」を「肘関節は屈曲を最小限」のような解剖学的書き換えにしない。原文のまま引用する）。
- 過去フィードバックとのクロスリファレンス（活性／抑制分類との突合せ等）は**しない**。やるとサマリが膨らむうえ、過去ファイルとの不整合を作りかねないため。
- 「主旨」「総括」のような俯瞰セクションは作らない。**箇条書きの行動リスト**だけで構成する。
- 1 セクションあたり 5 行程度を目安にする。原文より長いサマリは作らない。
- 動画 URL は **削らずに保持**（`menu_list.md` でも参照される一次ソースのため）

### 6. 完了時のユーザー報告

書き込み後、以下を 1〜2 行で伝える：

- どのパスに保存したか（新規 or 追記）
- `docs/content/` への反映候補があれば「次に反映するなら〜が候補」と一言

長い要約を会話に貼り直す必要はない。中身はファイルを開けば見られる。

## やらないこと

- `docs/content/` 配下のファイルを更新する（これは別作業。ユーザーが明示的に「反映までやって」と言ったときだけ別途対応）
- 原文の整形・誤字修正・改行調整・絵文字コードのデコード（原文は触らない）
- 既存ファイルの上書き（同日は追記）
- ファイル名のサフィックス追加（同日は単一ファイル `YYYYMMDD.md` に集約）
- 原文に出ていない筋名・キュー・解釈の追加
- 過去フィードバックとの突合せ・整合性チェック

## 参考：このリポジトリの命名規則

- フィードバックファイルは `YYYYMMDD.md` 形式。日付不明分は `YYYYxxxx.md`（例：`2025xxxx.md`）
