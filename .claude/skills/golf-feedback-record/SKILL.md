# golf-feedback-record

ゴルフレッスンのフィードバックを `resource/golf/feedback/YYYYMMDD.md` に蓄積するためのスキル。`trainer-feedback-record`（ジムのトレーナー用）と同じ設計で、対象と保存先だけが違う。

このリポジトリでは**フィードバックの原文は改変せずに残し**、公開ページ `docs/content/golf.md`（自分用マニュアル）への反映は別作業として切り分けている。`golf.md` は原文の転記ではなく「項目別に何を意識するか」を言い換えて積み上げるページなので、原文の保管とは役割が異なる。このスキルは**原文の保管**と、**次の練習・ラウンドで意識することに絞った短いサマリ**だけを担う。

## 発火する状況

ユーザーが以下のような入力をしたら、このスキルを使ってファイルへ保存する：

- レッスン中・直後にコーチから言われた内容をテキストでまとめてきた
- レッスンアプリ・LINE・メールなどで届いたコーチのコメントを貼り付けてきた
- 「今日のレッスンを記録して」「これゴルフの feedback に入れて」のように明示された
- 入力に「グリップ」「アドレス」「テイクバック」「コック」「フェース」「スイング」などゴルフ固有の語が並び、レッスンでの指導内容だと分かる

ユーザーがラウンドの感想・スコアの話・道具の相談をしているだけのときは、このスキルは使わない。**ジムのトレーナーからのフィードバック**は `trainer-feedback-record` スキルの担当なので、このスキルでは扱わない。

## 手順

### 1. 当日の日付・時刻を確認する

`date +%Y%m%d` をシェルで実行して当日の日付（例：`20260905`）を取得する。システムプロンプトの `currentDate` を流用しない（時差や日跨ぎでズレるため）。ファイル名はこの日付＋`.md`。

ユーザーが「先週のレッスンの分」のように**過去日**を明示してきた場合のみ、その日付を使う。曖昧なら確認する。

同日追記用の時刻は `date +%H:%M` で取得。

### 2. 保存先パスを決める

```
resource/golf/feedback/YYYYMMDD.md
```

ディレクトリが無ければ作る。

### 3. 既存ファイルの有無で処理を分ける

- **存在しない場合** → 新規作成
- **存在する場合** → 末尾に区切り線を入れて追記する（同日複数回の指導は順序情報も価値があるため上書きしない）

```markdown
---

## 追記（HH:MM 頃）

（以下、新しい原文＋サマリ）
```

### 4. 書き込む内容

ひとつのフィードバックブロックは次の構造で書く。**サマリは短く、行動に絞る**ことを最優先にする：

```markdown
# YYYY-MM-DD ゴルフレッスンフィードバック

## 原文

（ユーザーが貼り付けたテキストをそのまま貼る。整形・誤字修正・箇条書き記号の置き換えは一切しない）

## 次の練習・ラウンドへの反映

### 項目別の意識ポイント
- **項目名** — 意識すること（**原文に出ているキューのみ**）

### docs/content/golf.md 反映候補
- どの項目（見出し）に何を追記・修正すべきかを 1〜3 件
```

「項目別の意識ポイント」の**項目名は `docs/content/golf.md` の見出しと揃える**。使う名前は次のとおり（スイングの流れ順）：

グリップ／アドレス／テイクバック／トップ／ダウンスイング／インパクト／フォロースルー／フィニッシュ／その他（コース戦略・メンタル・練習法など、スイング局面に属さないもの）

原文に該当する記述がない項目は**書かない**（無理に埋めない）。原文の 1 つの指摘が複数項目にまたがる場合は、主に関係する項目に置く。

### 5. サマリ作成時の鉄則

このスキルでは「短く、書いてあることだけを書く」が最優先。以下を厳守：

- **原文に書かれていることだけ**を要約する。推測・補足・一般論・「これはスライス対策だろう」のような**読み解き**は一切足さない。書かれていないなら書かない。後から「これは AI の解釈」と分からなくなるのを防ぐため。
- **ゴルフ用語は原文の表記をそのまま使う**（例：原文が「コック」なら「コック」のまま。「手首の背屈」のように勝手に言い換えない。「ストロング」を「フックグリップ」に置き換えない）。
- **キューを言い換えない**（原文のまま引用する。言い換えて整理するのは `golf.md` に反映するときの仕事）。
- 過去レッスンとのクロスリファレンス（「前回と矛盾する」等の突合せ）は**しない**。やるとサマリが膨らむうえ、過去ファイルとの不整合を作りかねないため。
- 「主旨」「総括」のような俯瞰セクションは作らない。**箇条書きの行動リスト**だけで構成する。
- 1 項目あたり 3 行程度を目安にする。原文より長いサマリは作らない。
- 動画・画像の URL は**削らずに保持**する。

### 6. 完了時のユーザー報告

書き込み後、以下を 1〜2 行で伝える：

- どのパスに保存したか（新規 or 追記）
- `docs/content/golf.md` への反映候補があれば「次に反映するなら〜が候補」と一言

長い要約を会話に貼り直す必要はない。中身はファイルを開けば見られる。

## やらないこと

- `docs/content/golf.md` を更新する（これは別作業。ユーザーが明示的に「反映までやって」「マニュアルにも入れて」と言ったときだけ別途対応する。反映するときは原文転記ではなく、既存見出しの項目に**意識ポイントとして言い換えて**追記し、末尾の「レッスン履歴」表に日付とテーマを 1 行足す）
- 原文の整形・誤字修正・改行調整・箇条書き記号の置き換え（原文は触らない）
- 既存ファイルの上書き（同日は追記）
- ファイル名のサフィックス追加（同日は単一ファイル `YYYYMMDD.md` に集約）
- 原文に出ていない用語・キュー・解釈の追加
- 過去レッスンとの突合せ・整合性チェック

## 参考：このリポジトリの命名規則

- フィードバックファイルは `YYYYMMDD.md` 形式。日付不明分は `YYYYxxxx.md`（例：`2026xxxx.md`）
- ジムのトレーナーフィードバックは `resource/trainer/feedback/`、ゴルフは `resource/golf/feedback/` と、対象ごとにディレクトリを分ける
